# 角色视频转游戏动画工作流程

更新时间：2026-10-29。维护职责：05美术；程序接入由06负责，独立测试由07负责。

本流程用于把用户认可的角色视频转成可在棋盘上播放的透明动画，并交接给后续会话。默认沿用现有视频，不重新生图、重绘角色或生成视频。**先完整解码和检查，再处理透明背景、时序、尺寸、声音，最后在用户确认的场景中验收。**

这是一套工作流程，不是已经实现的通用一键转换器。熊山君案例提供了可参考的素材修复脚本和独立Godot播放器，但其中的帧数、时间、局部蒙版和棋盘参数不能直接套到其他角色。

## 一 开始前确认范围和来源

新会话先按 [AGENTS.md](../AGENTS.md) 顺序读取项目状态、决策日志及自己职责的工作流，再读取本文和本次素材说明；只打开与本次转换有关的媒体，不扫描全项目角色。

检查Git工作区、分支和远端，遵守共享Local文件所有权。已有来源不明改动不能覆盖或混入提交。当前会话不能只依赖聊天记忆：用户认可的版本、处理参数和实际交付必须落到仓库。

从当前用户授权和项目记录确认以下内容；记录已明确的答案，只有真正缺失的关键项才问用户：

| 项目 | 需要确定的内容 |
| --- | --- |
| 输入 | 哪个视频版本已认可；原件和修改版的关系；是否有参考首帧 |
| 动作 | 普攻、技能或其他动作；一次动作还是循环；角色自身的左右与屏幕左右分别是什么 |
| 目标 | 只做独立展示，还是接入现有游戏战斗；独立展示不自动获得改正式游戏的授权 |
| 场景 | 使用哪个棋盘版本，最好有用户确认过的实图；必要时查独立分支，不能只搜当前主分支 |
| 画面 | 保留角色造型、颜色和武器；是否明确允许局部修补、补帧或重绘 |
| 时间和声音 | 是否保持认可视频节奏；使用视频原声、独立攻击声还是静音 |
| 输出 | 目标平台、游戏内显示大小、透明帧／图集／可运行展示，以及存放目录 |

原件原样保存在项目候选目录，记录文件名、SHA-256和用户认可情况；加工结果另存。不要把原图重绘当作缩放，也不要把换色当作去白边。

## 二 检查工具和完整解码

需要视频解码工具、支持RGBA的图像处理环境，以及目标游戏引擎。推荐沿用现有 `video2dsprite` 流程，但先读取当前会话实际可用的技能和工具说明，不硬编码另一台机器的安装路径。Python须确认NumPy和Pillow可用；系统Python未必包含它们。FFmpeg和FFprobe需分别确认，缺少其中一个就如实记录，不宣称检查已运行。

先记录视频分辨率、解码帧数、每帧时间戳、视频轨结束时间、音轨起始时间／长度／采样率／声道数。**容器总时长、视频轨时长和音轨时长可能不同。** 可变帧率不能只按名义FPS平均分配时间。

以下是有FFmpeg／FFprobe时的命令形式，变量由执行会话设为本次真实路径；输出使用新目录，避免覆盖：

```sh
# SOURCE_VIDEO 指向已认可的视频；FRAME_DIR、META_DIR 是本次新建目录。
ffprobe -v error -show_streams -show_format -of json "$SOURCE_VIDEO" > "$META_DIR/streams.json"
ffprobe -v error -select_streams v:0 -show_frames \
  -show_entries frame=best_effort_timestamp_time,duration_time,pkt_duration_time \
  -of json "$SOURCE_VIDEO" > "$META_DIR/frame-times.json"
ffmpeg -i "$SOURCE_VIDEO" -map 0:v:0 -fps_mode passthrough "$FRAME_DIR/frame_%06d.png"
```

核对解码图片数量与帧时间记录一一对应。没有FFprobe时可用已验证的FFmpeg时间戳输出替代，但必须保存映射并检查，不能猜FPS。将所有输出时间归一到共同的视频起点；保留音频相对该起点的偏移。

**默认先保留全部原始帧。** 可以先用少量关键帧诊断抠像，但最终动画不能因此默认只交关键姿势。确需减少帧数时，在完整素材基础上对比连续效果、体积和性能，保留快速挥击过程；重复相同帧或提高播放速度不等于补回运动。不得为节省处理量擅自降低用户已认可的流畅度。

## 三 先判断源视频是否可用

制作完整帧表和正常速度预览，重点看动作开始、蓄力、挥击、收尾及首尾切换：

- 角色、手脚、武器是否变形、换色、换手或穿插；攻击方向是否正确。
- 镜头是否移动、放大或抖动；人物是否被逐帧缩放。
- 身体或武器是否出画，模糊部分是否仍有可恢复的画内信息。
- 背景、挥击弧、阴影、闪光是否与主体重叠，能否可靠分离。
- 是否有过长停顿、动作缺口、声音错位或意外音乐。

对真实出画、遮挡或角色变形，单纯扩大画布、缩小图像、去背景都不能恢复缺失内容。记录具体源帧与时间，选择可交付的受限试验或提出必要的局部修复／换源方案。**不能静默跳过坏帧后宣称动作完整，也不能未经授权重新生成角色。**

## 四 制作透明素材并清理边缘

先在原始分辨率建立透明蒙版，再统一缩放导出。保持同一角色各帧的处理参数一致；局部例外必须记录原因和范围。

1. 分离背景与主体，保留真实毛发、武器尖角和运动模糊的软透明边缘。颜色键不适合直接区分同为浅色的背景和银甲／绷带。
2. 检查轮廓内孔洞、残余灰块、孤立像素及地面阴影；不要把背景上的阴影当角色脚部，也不要重复叠两层阴影。
3. 检查边缘RGB污染。透明蒙版存在不代表去底完成：浅背景混入毛发、棍头和半透明像素，放到深色棋盘上会显出白圈。
4. 必要时做局部去污染，用附近可靠主体颜色估计边缘前景并保留软透明度。真实银甲高光必须保护，不能全身降亮度、整圈侵蚀或直接把所有灰白像素删除。
5. 检查挥击弧覆盖身体的区域。原视频已把特效与腿脚混在一起时，只能做有限近似分离；局部去雾参数需有明确蒙版，避免改变脸、服装或护甲。
6. 为全部帧生成深色、浅色和目标棋盘背景的对照，再按实际游戏大小查看。单张透明PNG、数值指标和白底预览都不能替代这些检查。

诊断闪白时，先判断它存在于素材还是运行程序。若PNG在深底合成时已经闪白，应修素材；若PNG正常，再检查引擎的透明混合、纹理采样、亮度调制和帧切换。不要用运行时整体变暗掩盖素材问题。

熊山君的 [去白边脚本](../godot-demo/art/candidates/bear_lord_matte_v2/build.py) 可复建现有20帧的修复，**不是任意视频通用抠像器**。它依赖旧候选的散列、384×320画布、背景估计及第10–12帧脚部椭圆区域；新视频、新帧数或新角色必须重新建立依据，不能原封不动运行。

## 五 固定画布 脚点和棋盘比例

整个动作使用同一张画布、同一缩放和同一平移。画布应容纳全动作及必要边距；记录 `sourceSize`、导出尺寸和脚锚。不要逐帧按非透明边界紧裁或自动拉满，这会造成身体忽大忽小、脚点漂移。腾空／踏步属于动作，不应靠逐帧锁脚强行抹掉。

用已确认棋盘的实际视口、格子几何和参照角色校准尺寸。比较角色**可见身高和脚部支撑范围**，不能把不同画布素材的缩放系数直接互抄。脚部支撑应符合约定占格，头顶和武器自然伸出格子不等于占多个格子。攻击全过程都要看，不只看首帧。

缩小时采用适合透明图像的重采样；内部预乘处理和导出的alpha约定必须清楚，避免重复预乘／反预乘产生黑白边。输出PNG通常使用直通道RGBA，按目标引擎实际合成验证。像素画与高清画的采样策略不同，不擅自换画风。

## 六 保留动作时间并同步声音

每帧元数据至少保存源帧编号、源时间、输出时间／持续时间、图像文件及散列。可变帧率相邻帧持续时间由时间戳差得到，最后一帧用视频轨实际结束边界；不要用音轨较长的尾部替代画面时长。

- **独立动作展示：** 默认保持认可视频的时间，不套用战斗冷却或技能时长。循环间隔明确记录，首尾应看是否突跳；不能靠倒放攻击恢复待机。
- **修改节奏：** 只改用户指定段落，音画使用同一时间映射。保留原件和修改说明。
- **视频原声：** 提取认可版本的音轨，从每轮动画起点同步播放整轨；不是到命中帧才启动整轨。计算音频相对视频起点的偏移，正偏移补静音或延迟，负偏移按共同时间线裁切；编码补齐和尾部也要核对。
- **独立攻击声：** 才按挥击／命中事件触发；不与视频原声重复叠加，除非用户要求。
- **循环和暂停：** 保证音轨不会跨轮叠放；若支持暂停、倍速或重播，检查音画是否一起变化，不能只改画面时钟。

提取未对齐音轨的命令形式如下；这一步完成后仍须按上述规则处理起点，不能把WAV从0秒开始等同于源视频已对齐：

```sh
ffmpeg -i "$SOURCE_VIDEO" -map 0:a:0 -vn -c:a pcm_s16le "$AUDIO_OUT"
```

先确认视频是否有音轨。保留原声时不要自动加入鼓点、背景音乐或其他效果。时标／波形检查能验证同步，但不能代替实际听感。

## 七 先交付明确范围的可运行展示

若目标是单角色展示，使用独立项目或独立入口：确认的棋盘、一只角色、指定动作及声音即可。不要顺手加载整场战斗、敌人、伤害系统或修改旧游戏默认入口。

运行资源与制作源分开，正式运行目录只放需要的帧、元数据、场景和音频。候选目录的 `.gdignore` 可能让Godot完全忽略素材，必须显式复制或导入需要的资源。记录复制关系和散列。

播放器按时间戳选择当前帧；不能假设固定20帧、均匀间隔或固定动作时长。全套资产按需预加载，减少播放中解码卡顿；更多帧是否需要图集、压缩或分辨率分档，应以实际内存和运行效果决定。

当前 [熊山君独立展示](../bear-forehand-showcase/README.md) 通过 `clips.json` 配置各动作的manifest、原声、视频轨时长、循环间隔和显示倍率；帧数、画布、脚锚与时间戳从各manifest读取，已移除播放器固定20帧的约束。它直接读取原始PNG/WAV以支持无导入缓存的源码启动，**不因此自动成为可发行包**。导出时仍须显式纳入这些原始文件，并在脱离源码目录的实际包中验证。复用到新角色时，需调整配置、方向定义及测试预期。

用户授权镜像补方向时，围绕角色固定脚锚水平翻转画面；不翻转帧序，也不交换音轨声道。前视角和后视角分别保留自己的时间线、原声与比例；切换方向停止上一段声音、将新动作与声音同时重置到起点。核对镜像前后脚锚世界坐标相同，不能围绕PNG中心翻转导致站位横跳。镜像会反转持械侧和服饰的不对称细节，这与新增独立绘制方向不同，必须符合当前授权。

只有用户要求正式接入游戏时，才由06继续处理与战斗状态机相连的待机／攻击／受击切换、移动和脚点、命中事件、取消中断、攻击间隔及音频触发。独立展示可以在已授权范围内验证方向与镜像。画面进入挥击帧与真实伤害结算是两个环节，不能用动画长度偷偷修改战斗数值。

## 八 验证通过后再交付

| 检查层 | 必须确认的内容 |
| --- | --- |
| 文件与来源 | 原件未变；输入版本正确；帧数／尺寸／元数据对应；透明边界、非空、散列及复制关系正确 |
| 视觉 | 全帧深浅底、关键相邻帧、正常速度循环；无明显白圈、闪白、残底、缺肢、武器缺失或忽大忽小 |
| 场景 | 用户确认的棋盘；实际尺寸下脚点、比例、遮挡和方向正确；只包含授权范围的角色和界面 |
| 时间与声音 | 时间戳单调；首尾和循环正确；原声起点／尾部／重复触发正确；必要暂停倍速测试 |
| 运行 | 无 `.godot` 等本机缓存的干净副本能首次启动；只有程序退出码0不足以证明画面已加载 |
| 实际体验 | 专用窗口真实画面及连续播放，声音按授权试听；静态采样与真实连续观感分别记录 |
| 导出 | 若交付资源包／安装包，独立目录检查包内资源、入口、播放及目标平台，不借源码目录补资源 |

只运行与本次改动相关的必要检查。修透明帧不必反复跑整套战斗，但必须复核真实游戏大小下的边缘。多人协作可并行只读评审；修改同一文件时串行，按AGENTS归属维护工作流。

不要把“去白像素数量下降”“透明边界合格”“脚本测试通过”写成视觉完全合格。记录源视频无法自动恢复的缺口、仍有的模糊和用户尚未确认的观感。测试失败或工具不可用要保留真实结果，不把未执行的步骤算通过。

## 九 保存和跨会话交接

每套素材集中维护一份README，包含输入来源与散列、用户认可的版本、处理脚本／依赖／参数、时间与音频映射、画布与脚锚、棋盘版本、输出文件、运行入口、实际验证、已知限制和下一步。必要的可复建脚本和有效对照图进入仓库，不能只放 `/tmp` 或聊天附件。

05维护素材及本工作流，06维护运行接入，07维护独立验收。各自工作流只写摘要并链接权威说明，跨领域确认写入“待总控同步”。完成必要检查后按项目授权提交并推送；不得混入他人文件。推送失败时明确本地提交号和未同步状态，另一台机器读取不到的内容不能称已完成跨机器交接。

建议每套交付保留这些类别，命名可按项目已有约定调整：

```text
素材候选目录/
  README.md                 来源、处理方法、范围和限制
  source/ 或原件引用         已受版本管理的认可视频
  build.py 等               可复建的转换／修复代码和参数
  frames/ 或平铺PNG          固定画布透明动画帧
  manifest.json             帧编号、时间、尺寸、锚点、来源和散列
  audio/                    需要时保存对齐后的原声
  review/                   全帧深浅底、前后对照及必要真实运行证据
独立展示目录/
  README.md、启动入口、场景、运行素材
```
